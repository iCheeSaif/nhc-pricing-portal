# منصة تسعير شراكات — تطبيق ويب مستقل

**Standalone Pricing Portal** · Arabic RTL · FastAPI + SQLite + HTML/CSS/JavaScript

هذا مشروع ويب قابل للتشغيل بشكل مستقل، وليس ServiceNow Portal ولا يعتمد على اتصال بشبكة NHC. تم بناؤه بالاستناد إلى «وثيقة متطلبات الأعمال لنظام التسعير (شراكات) – التسعير المبدئي»، نسخة 1 أكتوبر 2026 (44 صفحة).

## تشغيل الموقع

يتطلب **Python 3.11 أو أحدث**. على macOS يمكن الضغط مرتين على `start-mac.command`، وعلى Windows يمكن تشغيل `start-windows.bat`. أو من داخل مجلد المشروع:

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app:app --host 127.0.0.1 --port 8000
```

افتح **http://127.0.0.1:8000** في المتصفح.

يمكن تشغيله أيضًا عبر Docker بعد ضبط متغيرات البيئة:

```bash
docker build -t pricing-portal .
docker run --rm -p 8000:8000 \
  -e APP_ENV=production \
  -e SECRET_KEY='CHANGE_TO_A_LONG_RANDOM_SECRET_KEY_AT_LEAST_32_CHARACTERS' \
  -e INITIAL_ADMIN_PASSWORD='CHANGE_TO_A_STRONG_PASSWORD' \
  -v pricing-data:/app/data pricing-portal
```

> لا تنشر وضع `demo` على الإنترنت. عند الإنتاج، يجب إنشاء المستخدمين من حساب الإدارة، ضبط `APP_ENV=production`، و`SECRET_KEY` ثابت وآمن، وتمرير كل الزيارات عبر HTTPS خلف Reverse Proxy.

## السيناريو الكامل

1. **الوجهات والميزانيات**: إنشاء الوجهة والمدينة، وتعريف أكثر من اتفاقية خصم بنية تحتية أو قسط ميسر، ومتابعة المستخدم والمتبقي والتحذير عند 90%.
2. **اتفاقيات التطوير**: تسجيل رقم العقد والمطور ونموذج الاتفاقية ومعلومات المساحة، وربط اتفاقية واحدة بمشروع.
3. **المشاريع**: اختيار وجهة واتفاقية، وتحديد نوع المشروع (أرض وزارة أو شركة).
4. **التسعير المبدئي**: إنشاء طلب نوع `base`، واستيراد وحدات من Excel الداخلي أو إضافتها يدويًا، ومعاينة الأسعار، وإرسالها للـChecker. لا تُنشأ الوحدات الفعلية إلا بعد الاعتماد.
5. **تغيير الأسعار**: يمكن تحديد أسباب طلب التغيير من القائمة متعددة الخيارات. إنشاء طلب نوع `price` على وحدات موجودة؛ تعديل معدلات الأسعار والخصومات والزيادات واختيار ميزانيات الخصم، ثم Checker، وبعده سبعة موافقين بالترتيب. التطبيق النهائي يحدث فقط بعد آخر موافقة.
6. **تغيير التصاميم**: إنشاء طلب نوع `design` مع تعديل مساحة أو خصائص وحدات، أو إضافة/حذف وحدات، وتحديث الحسابات مع الاحتفاظ بالمدخلات والخصومات السابقة؛ يعتمد من Checker دون سلسلة إضافية.
7. **المقارنة والتاريخ**: عرض اختلافات الحقول بين طلبين من نفس المشروع والنوع، وسجل سابق/لاحق لكل تغيير وحدة، وسجل القرارات.
8. **التقارير**: مؤشرات الطلبات، مجموع الأسعار لكل مشروع، متابعة ميزانيات الخصومات، وتصدير الوحدات إلى XLSX.

## قائمة الجداول (SQLite)

- `users`: المستخدمون والأدوار.
- `destinations`: الوجهات والمدن.
- `agreements`: اتفاقيات التطوير.
- `projects`: المشروع وربطه بالوجهة والاتفاقية.
- `budgets`: اتفاقيات ميزانيات الخصومات.
- `units`: البيانات والأسعار **المعتمدة** الحالية.
- `requests`: الطلبات (base / price / design).
- `request_items`: نسخ الوحدات قبل التغيير وبعده (pending snapshots).
- `approvals`: خطوات الموافقة والقرارات.
- `budget_ledger`: حركة الخصومات **عند الاعتماد النهائي**.
- `audit`: سجل نشاط غير مخصص للتعديل عبر API.
- `unit_history`: سجل تاريخي قبل/بعد لكل وحدة.

التصميم يستخدم 12 جدولًا عمليًا بدل إنشاء جدول لكل طريقة تسعير. صيغة الأسعار محفوظة بشكل واضح داخل `pricing_json` مع كل وحدة. جميع حسابات السعر في الدالة المركزية `calculate()` بملف `app.py` ولا تتم حسابات مالية مؤثرة في واجهة المتصفح.

## القواعد المنفذة

- **شامل**: مساحة البيع × سعر المتر الشامل (ثم تقسيم قيمة الأرض والبنية التحتية وإظهار باقي قيمة البناء).
- **مفصل**: (مساحة البيع × سعر متر البناء) + (مساحة الأرض المعتمدة × سعر متر البنية التحتية) + (مساحة الأرض المعتمدة × سعر متر الأرض الخام).
- **شامل مع التخصيص**: إعدادات الباقة (البناء/البنية، البناء/الأرض، البنية/الأرض) باستخدام المدخلات المجمعة بالباقة؛ التفاصيل تحتاج توثيق المعادلات من الأعمال.
- **الشقق**: حساب حصة أرض البلوك بواسطة NSA؛ إضافة المساحة المشاعة ومعامل `0.2941` في مسار مشاريع الوزارة، وحسم حصة التجاري في مسار مشاريع الشركة. هذا **تنفيذ مبدئي** لطريقة التخصيص يستلزم تأكيد المعادلات والبيانات من قطاع شراكات.
- **الخصومات**: منع قيمة الخصم من تجاوز قيمة العنصر، ومنع زيادة التدرج مع خصم البنية التحتية أو القسط الميسر، وعدم انخفاض الوحدة تحت 250,000 ر.س عند خصم القسط الميسر.
- **التحكم بالوحدات**: لا تغير سعر/تصميم وحدة محجوزة أو مباعة. لا يعدل صاحب الطلب أسعار الوحدات المعتمدة مباشرةً. سجل التدقيق والمعاملات يطبقان في قاعدة البيانات.
- **الميزانيات**: منع الخصم الذي يتجاوز إجمالي الميزانية، وإظهار تنبيه بعد بلوغ 90%، وتسجيل الخصم في دفتر صرف مستقل عند الاعتماد النهائي فقط.
- **صلاحيات**: Maker ينشئ ويعدل طلباته، Checker يراجع ولا يعتمد طلبه الشخصي، ثم سلسلة الموافقة المهنية؛ يمنع التعديل بعد الإرسال ما لم يعاد الطلب. يوجد CSRF/session cookies وكلمات مرور PBKDF2.
- **حد نسبة 25% لغير المستفيدين في مشاريع الوزارة**: **تحذير مراجعة وليس منعًا** حتى يتضح من مالك العمل الفرق بين *عرض سعر غير المستفيدين* و*تخصيص وحدات البيع لغير المستفيدين*؛ لا يجوز اتخاذ قرار تلقائي غير مؤكد من الحقول الحالية.

## الحدود / التكاملات غير المكتملة

**هذا تنفيذ وظيفي standalone، وليس جاهزًا لبيئة إنتاج مالية دون مراجعة واختبار واعتماد إضافي.** هناك نقاط لا يمكن إتمامها بأمان دون مدخلات خارجية:

1. **PPM integration الفعلي والمزامنة اليومية:** لم تُقدَّم API endpoints أو Auth أو نموذج بيانات PPM. يمكن إدخال الاتفاقيات يدويًا الآن. الربط الآلي يتطلب وثيقة API وبيانات اتصال معتمدة.
2. **CRM integration:** محدد في وثيقة الأعمال كمرحلة قادمة؛ غير مُنفَّذ في هذه النسخة.
3. **نموذج «إتمام» الرسمي ونموذج تغيير الأسعار:** لم يُرفقا، لذلك أعددنا قالب XLSX مستقلًا داخل الموقع. يحتاج المستورد لاحقًا Map للأعمدة وفق الملف الحقيقي.
4. **الصيغ الخاصة بكل اتفاقية وتفاصيل تخصيص أسعار الشقق:** توجد حالات تحتاج قرارات مؤكدة بشأن طريقة توزيع المتغيرات والحزم والمناطق التجارية، وقاعدة السقف للدعم العيني. الصيغ الأساسية منفذة، وتفاصيل الحزم تتطلب مصادقة فريق الأعمال.
5. **مقارنة طلبي تسعير قبل الاعتماد:** موجودة كشاشة مستقلة. لم نجعلها شرطًا قاطعًا لإكمال أول طلب، لأن الوثيقة تطلب مقارنة طلبين حتى عندما قد يوجد طلب واحد أولي؛ يلزم حسم المطلوب.
6. **دورة طلب التغيير في التصاميم:** اعتماد Checker موجود، والخطوة المقترحة لإنشاء طلب أسعار مرتبط تُتاح عبر اختيار مشروع ونوع طلب جديد. الزر المختصر المباشر غير مضاف.
7. **المراسلات والإشعارات البريدية وملفات التخصيص التعاقدية الرسمية** تحتاج SMTP وأسماء مجموعات/مستخدمين فعليين.
8. **حالات اختلاف الموافقات حسب الاتفاقية** تحتاج Confirmation من مالك الأعمال قبل تخصيص workflow.
9. **نضج التشغيل**: للتشغيل الداخلي الحقيقي يلزم اختبارات حمل، نسخ احتياطية، إجراءات استعادة، تدقيق أمني، سياسات رفع الملفات، مراقبة التشغيل، وسجل خاص باستثناءات الأعمال.

## التوصية للنشر

- بيئة تجريبية داخلية: Docker + volume للبيانات + HTTPS عن طريق Reverse Proxy.
- إنتاج مؤسسي متعدد المستخدمين: يُنصح بـ PostgreSQL بدلاً من SQLite عند رفع الحمل أو تعقيد التشغيل؛ تعديل طبقة قاعدة البيانات ليس ضمن النسخة الحالية.
- النسخة لا تحتوي خدمات سحابية أو اتصالات طرف ثالث وتعمل بدون شبكة خارجية؛ تحميل الخط من Google Fonts اختياري ويمكن استبداله بالخط المحلي الاحتياطي.
